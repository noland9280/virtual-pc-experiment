# Virtual PC Experiment

**ブラウザだけで完結する「Ubuntu仮想PC」を、GPU無し・Docker無しの環境から作る実験記録**

GitHub Codespaces(無料枠)の上に、KDE Plasmaデスクトップをフルに動かし、
ブラウザだけでWindowsアプリ(Wine経由)やRoblox Studioまで触れる環境を構築した、
個人開発の記録とハウツーです。

- ローカルPCにDockerを入れられない
- Roblox Studioを動かせるPCを持っていない

という制約から始まった、「じゃあブラウザから動かせばいいのでは」という発想の実験です。

> ⚠️ これは個人の実験記録です。安定した実運用を保証するものではありません。
> GitHub Codespacesの無料枠(個人アカウントで月120コア時間)を前提にしています。

### ⚠️ GitHubの利用規約について(重要)

このプロジェクトを試す前に、必ず一読してください。

GitHubの公式規約([GitHub Terms for Additional Products and Features](https://docs.github.com/en/site-policy/github-terms/github-terms-for-additional-products-and-features)、Codespacesの項)には、Codespacesの使用を禁止する行為として、次のようなものが明記されています(要約):

- クリプトマイニング
- 他のサービス・デバイス・データ・アカウント・ネットワークへの不正アクセス(妨害を含む)
- Codespaces自体(またはその一部)を商用サービスとして単体・統合提供すること
- サーバーに対して、ユーザーへの便益と釣り合わない負荷をかける行為
  (例: CDNとして使う、サーバーレスアプリの一部として使う、**本番運用のアプリケーションをホストする**など)
- **Codespacesを起動したリポジトリに紐づくソフトウェアプロジェクトの開発・テストと
  無関係な、その他あらゆる活動**

違反した場合、GitHubはCodespacesへのアクセス制限・停止や、該当リポジトリの
無効化などの措置を取れるとされています。

**正直な評価**: このプロジェクトの使い方(汎用デスクトップとして使う、Roblox Studioで
遊ぶなど)は、上記の「ソフトウェア開発・テストと無関係な活動」に該当しうる、
本来の用途からは外れたグレーゾーンの使い方です。試す場合は、この点を理解した上で
**自己責任**で行ってください。特に以下のような使い方は、規約違反として扱われる
リスクがより高いと考えられるので避けるべきです。

- 常時稼働させ続けて、普段使いのPCの代わりとして運用する
- 画面や音声配信のポートを不特定多数に公開し、他人にサービスとして提供する
- 本番運用のアプリケーション・Webサイト・ゲームサーバーなどをホストする

不明な点があれば、[GitHub Support](https://support.github.com/)に直接問い合わせることを推奨します。

### 似たプロジェクトとの位置づけ

「Codespaces上でブラウザ完結のデスクトップを動かす」というコンセプト自体は、
探してみると他にも前例がある(`noVNC` + 軽量ウィンドウマネージャの組み合わせなど)。
このプロジェクトが独自に踏み込んだのは、主に以下の部分:

- 軽量WMではなく、KasmVNC経由でフル機能のKDE Plasmaデスクトップを動かしている
- システム音声をHTTPストリーム配信する仕組みを自作している(Selkies標準のWebRTC音声は
  Codespacesのポート制約で使えないため)
- Wine経由でWindowsアプリ(Roblox Studio)を動かし、ブラウザ⇔アプリ間のログイン連携
  (`roblox-studio-auth`プロトコルハンドラー)まで構築している
- コンテナのリビルドを跨いでも、デスクトップ設定・Wine環境・ブラウザのログイン状態が
  消えないよう永続化する仕組みを作り込んでいる

## 前提知識(初めての方向け)

このガイドでは、以下の用語が頻繁に出てきます。すでにご存知の場合は読み飛ばしてください。

- **GitHub Codespaces**: GitHubが提供する、クラウド上の開発環境。本来はコードを書くための
  サービスだが、中身はLinuxコンテナ(≒使い捨てできる小さな仮想マシン)なので、
  工夫すればデスクトップ環境を丸ごと動かすこともできる。個人アカウントには
  無料で使える時間枠(2026年現在、月120コア時間)がある
- **コンテナ / Rebuild(リビルド)**: Codespacesの実体は「コンテナ」と呼ばれる、
  軽量な仮想環境。「Rebuild Container」を実行すると、そのコンテナを一度破棄して
  設定ファイル通りに作り直す。**これが今回のプロジェクトで一番重要な注意点**
  (詳しくは下記「⚠️ リビルドする前に」を参照)
- **devcontainer.json**: Codespacesがコンテナを作るときに読む設定ファイル。
  「どのベースイメージを使うか」「起動時に何を実行するか」などを書く
- **KasmVNC**: リモートのLinuxデスクトップ画面を、専用アプリ不要でブラウザだけに
  表示する技術。今回のプロジェクトは、これを使ってCodespaces上のデスクトップ画面を
  ブラウザのタブに映している
- **Wine**: Linux上でWindows向けのアプリケーションを動かすための互換レイヤー。
  Windowsそのものを動かすわけではなく、「Windowsアプリが呼び出すWindowsの機能」を
  Linux側で肩代わりして実行する仕組み

## ⚠️ リビルドする前に: 保存を忘れると本当に消えます

これは実際に経験した話です。作業中のRoblox Studioのマップを保存しないままリビルドしたところ、
一部のデータが破損し、Studio側の自動復元機能に頼ることになりました(幸い大事には
至りませんでしたが、保証はできません)。

**「Rebuild Container」は、動いているアプリに「保存してから終了してください」と
頼んでくれるわけではありません。** コンテナを問答無用で終了させて作り直す処理なので、
書き込み途中のファイルがあれば、そのタイミングでそのまま失われる・壊れる可能性があります。

リビルドする前に必ず:

1. **開いているアプリ(Roblox Studio等)で明示的に保存する**(Ctrl+Sなど)
2. 可能であれば、**クラウド上に公開・アップロードしておく**(Robloxなら「発行」機能。
   一度クラウドに上がったデータは、コンテナの外にあるのでリビルドの影響を一切受けない)
3. アプリ自体を、右上の`×`など**通常のウィンドウ操作で閉じる**(強制終了しない)。
   `kill -9`やタスクの強制終了は、保存中の書き込みを中断させる可能性があるため避ける
4. ターミナル(Konsoleまたはvscodeのターミナル)で、ディスクへの書き込みを
   確実に完了させるために以下を実行してから少し待つ:

```bash
sync
```

5. それでもまだ不安な場合は、`sync`実行後に10秒ほど待ってからリビルドを実行する

「永続化」の仕組み(後述)でデスクトップの設定やWine環境自体は消えないように
してありますが、**アプリの中で「今まさに編集中だったデータ」までは守ってくれません**。
この違いを意識しておくことが大事です。

## 何ができるか

- ブラウザ**タブ3枚**(Codespaces管理画面・画面配信・音声配信)で、フル機能のKDE Plasmaデスクトップにアクセスできる
- 日本語UI・日本語入力(fcitx5 + Mozc)に対応
- 音声(PCのシステム音)をブラウザ側で再生できる(HTTP配信、数十秒の遅延あり)
- Wine経由でWindowsアプリを動かせる(Roblox Studioで動作確認済み)
- リビルド(コンテナの作り直し)をしても、デスクトップの見た目やログイン状態が消えない

## 何ができないか / 制約

- **GPUが無い**ため、3D描画はすべてソフトウェアレンダリング(`llvmpipe`)。重い3Dアプリは紙芝居レベルの速度になる
- Codespacesのポート転送はHTTP(S)専用。WebRTC(音声・映像のリアルタイム配信)は素の状態では動かない
- 無料枠を使い切ると、その月はそれ以上使えなくなる(翌月リセット)
- **無料枠は「コア時間」で計算される点に注意**。GitHubの個人アカウントの無料枠は
  月120コア時間だが、これはこのプロジェクトで使っている4コアマシン(`standardLinux32gb`)だと
  **実時間換算で月30時間**にしかならない(120 ÷ 4コア = 30時間)。
  「120時間使える」と勘違いすると、思ったより早く上限に達して驚くことになる

## 技術構成の概要

### ベース

- GitHub Codespacesの`devcontainer.json`から、Selkiesプロジェクトが提供する
  KDE Plasmaデスクトップコンテナイメージを起動する
- 画面配信には、そのイメージに含まれる KasmVNC(ブラウザ完結型のVNC実装)を使う。
  Selkiesプロジェクト本来のWebRTC配信(Selkies-GStreamer)は、Codespacesの
  ポート転送がHTTP(S)限定でUDP/TCPの生ポートを通さないため、この用途では使えない

### 画面・音声

- **画面**: KasmVNC(WebSocketベース)。ポート転送をPublicにすればブラウザから直接アクセスできる
- **音声**: Selkies標準のWebRTC音声もCodespaces上では動かないため、
  PulseAudioの出力を`ffmpeg`でmp3にエンコードし、単純なHTTPストリームとして配信する自作構成。
  ステレオ・64kbpsが、モノラル・低ビットレートより体感遅延が短いという実測結果あり

### 日本語化

- `LANG`/`LC_ALL`/`LANGUAGE`は、Codespacesのコンテナ起動時の環境変数(`containerEnv`)に
  直接設定する。あとから設定ファイルを書き換えても、コンテナの起動処理側で
  上書きされてしまうため、この方式が確実
- 日本語入力は`fcitx5` + `Mozc`

### 永続化(最重要ポイント)

Codespacesの「Rebuild Container」は、リポジトリのファイル以外(ホームディレクトリ、
インストール済みアプリ、開いていたアプリの状態など)を全て消してやり直す。
これに対応するため、消えてほしくないファイル・ディレクトリを、リポジトリの管理下にある
場所へのシンボリックリンクとして扱う方式を採用している。

永続化している主なもの:
- デスクトップの壁紙・アイコン・テーマ設定
- デスクトップ上のショートカット、アプリランチャー登録
- Wineのインストール環境一式(`WINEPREFIX`)
- Firefoxのプロファイル(ブラウザのログインセッション・Cookieを含む)

この仕組みのおかげで、コンテナを作り直しても、日本語入力設定やWine環境、
ブラウザのログイン状態などが毎回消えずに残る。

## つまずいたポイントと解決策

### 1. `apt install`が理由も分からず静かに失敗する

このコンテナ環境では、`fakeroot`のデフォルト方式(SysVセマフォ)が対応しておらず、
`apt-get install`が内部エラーで失敗することがある。エラーメッセージも分かりづらく、
`postCreateCommand`(コンテナ作成時に自動実行される処理)が理由不明で止まっているように
見えてしまう、いちばんハマりやすいポイントだった。

対処法(セットアップスクリプトの冒頭に固定で入れておく):

```bash
sudo update-alternatives --set fakeroot /usr/bin/fakeroot-tcp
```

### 2. `devcontainer.json`が壊れて「リカバリモード」になる

`devcontainer.json`はJSON形式なので、中に長いシェルコマンドを1行で詰め込むと、
エスケープのミスでJSON自体が壊れやすい。壊れるとCodespaceが正常に起動できず、
リカバリモードに入ってしまう。

対処法: セットアップ処理は極力`devcontainer.json`の中に直接書かず、
別のシェルスクリプトファイルに分離して、`devcontainer.json`側からは
そのスクリプトを呼び出すだけにする。

### 3. リビルドのたびにアプリが消える

apt installしたパッケージや、ホームディレクトリ配下のアプリ設定は、
`/workspaces`(リポジトリの中)以外の場所にあると、リビルドで全部消える。
これに気づかず「インストールしたはずなのに無い」と混乱することが何度もあった。

対処法は前述の「永続化」の通り。加えて、apt installしたコマンド類については、
サービス起動スクリプト側で「無かったら自動でインストールし直す」という
自己修復コードを入れておくと、リビルドのたびに手動対応しなくて済む。

### 4. GPUが無い環境での3D描画

GPU無し環境では、OpenGLの描画は`llvmpipe`というソフトウェアレンダラーで行われる。
これはCPUの全コアを使って描画をエミュレートする仕組みで、当然ながらGPUよりかなり遅い。

体感速度を上げるためにできること:
- 画面解像度を下げる(描画するピクセル数がそのまま負荷に直結する)
- アプリ側のグラフィック品質設定を下げる(影・アンチエイリアシングなど)
- `LP_NUM_THREADS`環境変数で、ソフトウェアレンダラーが使うスレッド数を
  コア数に合わせて明示指定する

> 💡 課金してより上位のマシンタイプ(8コア・16コアなど)を使う場合は、
> `LP_NUM_THREADS`もそのコア数に合わせて増やすこと。このプロジェクトは
> 無料枠の4コアマシンを前提に`LP_NUM_THREADS=4`としているが、コア数を
> 増やしても、この値を合わせて変更しないと余ったコアが活かされない。

### 5. VNC経由の日本語入力切り替え

リモートデスクトップ環境だと、キーボードショートカット(Ctrl+Spaceなど)が
ブラウザやOS側に横取りされて、リモート側まで届かないことがある。
`xev`コマンドでキー入力が実際にリモート側まで届いているかを確認しながら
切り分けるのが有効。

### 6. Wine経由のアプリが「重い」と思ったら、別プロセスの暴走を疑う

GPU無し環境でのソフトウェアレンダリングはもともと重いが、それにしても
おかしいレベルで重い・カクつくときは、レンダリング自体ではなく
**別のプロセスがCPUを食い尽くしている**ことがある。

実際に踏んだ原因は、エディタ拡張機能の`rg`(ripgrep、ファイル検索用)が、
Wine環境(`WINEPREFIX`)配下の大量のファイルをインデックス化しようとして
CPUに張り付き続けていたこと。`top`で確認したところ、1プロセスだけで
CPU使用率が100%を超えて張り付いていた。

見分け方:

```bash
top -bn1 | head -15
```

CPU使用率トップに見覚えのないプロセス(特に`rg`)が張り付いていたら、
一度killしてload averageが下がるか確認してみるとよい。

```bash
kill <PID>
```

再発防止には、エディタ側の検索・ファイル監視対象から`WINEPREFIX`配下を
除外しておくのが効果的(このリポジトリの`.vscode/settings.json`を参照)。

### 7. 音声配信(ffmpeg)が聞こえないときの確認手順

ブラウザ側で音声が聞こえない・音声再生ページが真っ白/エラーになる場合の切り分け手順。

**1. まず配信ポートが生きているか確認**

```bash
ss -tln | grep 8998
```

何も表示されなければ、そもそも配信プロセス自体が起動していない。

**2. ログを確認する**

```bash
cat /tmp/audio-stream.log
```

`ffmpeg`自体がエラーで落ちていないか、それとも単に起動直後でまだ間に合っていないだけか
(起動直後は一時的に「失敗」と表示されることがある)を確認する。

**3. サービスをまとめて再起動する**

このリポジトリの`start-services.sh`(デスクトップアイコン「サービス再起動」からも実行可)には、
ffmpegが万一無ければ自動でインストールし直す自己修復コードが入っているので、
まずはこれを実行してみるのが手っ取り早い。

```bash
bash /workspaces/<リポジトリ名>/start-services.sh
```

**4. 画面(KasmVNC)側も一緒に不安定なら、コンテナ起動直後のタイムラグを疑う**

画面配信(ポート8080)が一時的に502エラーになったり、Konsoleが開けなかったりする場合、
コンテナが完全に立ち上がりきる前にアクセスしてしまっている可能性がある。
`postStartCommand`のヘルスチェックログを見ると、起動シーケンスのどこで
つまずいているかが分かる。

```bash
cat ~/vpc-healthcheck.log
```

数分待ってから再度アクセスすると直ることが多い。
